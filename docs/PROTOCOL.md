# i6-share architecture & wire protocol (v1)

i6-share moves files between an **Android phone (or any Chrome)** and a **Linux PC** over the
local network only, with no internet server of any kind.

```
 ┌──────────────────────────────┐   HTTP over LAN (encrypted bodies)   ┌──────────────────────────────┐
 │ Phone: installed PWA         │ ───────────────────────────────────▶ │ Linux: i6-share Hub (IWA)    │
 │ https://krusegit.github.io/  │   fetch("http://192.168.x.y:47616")  │ Direct Sockets TCPServerSocket│
 │ i6-share/  (GitHub Pages)    │ ◀─────────────────────────────────── │ tiny HTTP/1.1 server on :47616│
 │ share target, QR pairing     │   responses / long-poll / pulls      │ saves files to a folder       │
 └──────────────────────────────┘                                      └──────────────────────────────┘
```

* A browser page cannot listen on a socket, so the **hub (IWA) is the only listener**; the phone
  always initiates. Hub → phone transfers are delivered by the phone polling (`/i6/sync`) and
  pulling (`/i6/pull`).
* The phone page is HTTPS (GitHub Pages) and talks to `http://<private-ip>:47616`. Chrome allows
  this under **Local Network Access**: the user grants "access devices on your local network"
  once, and requests to private-IP literals are exempt from mixed-content blocking.
* GitHub Pages only delivers the code. The service worker caches it; after that everything works
  offline on the LAN.

Inside the hub bundle, paths are: `/index.html`, `/hub.js`, `/…other hub files`, `/lib/*.js`,

Rules for all browser code: vanilla JS ES modules, no frameworks, no CDNs, no external requests,
no `innerHTML`/`eval`/inline scripts or inline event handlers (IWA CSP + Trusted Types). Use
`h()` from `lib/dom.js` to build DOM. Relative URLs only (Pages serves under `/i6-share/`).

## Identity & pairing

* **Phone** has a persistent random `deviceId` (16 hex chars, `randomId(8)`) and a user-editable
  name, stored in `kv`.
* **Hub** has a persistent random `hubId` (16 hex chars) and a name (default "Linux PC").
* Pairing is done once by scanning a QR code shown by the hub. The QR encodes
  `APP_URL#pair=<payload>` (`encodePairPayload` in `proto.js`): hubId, a **one-time 16-byte
  token**, port, the hub's private LAN IPv4 and unique-local (fc00::/7) IPv6 addresses (no link-local, no global IPv6 — Chrome treats those as public, so mixed-content rules block them), and its name.
  Scanning it with any camera app opens the PWA, which completes pairing. The PWA also has an
  in-app scanner (`BarcodeDetector`) and a "paste pairing code" fallback.
* The hub keeps each displayed token valid for `PAIR_TOKEN_TTL_MS` (10 min) and until used once.
  It rotates the token every time the QR is (re)shown or used.
* `/i6/pair` exchanges a fresh 32-byte random **device secret S** (generated by the hub),
  encrypted under `pairKey(token, hubId)`. After pairing, all traffic is encrypted and
  authenticated with `deviceKey(S, deviceId)`. Possession of S = trusted device: transfers are
  accepted and saved automatically, with no prompts.
* Pairing happens at the moment of the first transfer if needed: sharing to i6-share with no
  paired computer leads the user straight into "scan the QR on your PC", then the queued files
  send automatically.

## Transport

Base URL `http://<ip>:47616` (`baseUrl()`; IPv6 bracketed). Requests are deliberately CORS
"simple" (POST, `Content-Type: text/plain`, no custom headers) to avoid preflights, but the hub
**must** also answer `OPTIONS` preflights.

Every hub response includes:
```
Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: *
Access-Control-Allow-Private-Network: true
Access-Control-Max-Age: 86400
Cache-Control: no-store
```

### Unauthenticated

`GET /i6/hello` → `200 application/json`
```json
{ "app": "i6-share-hub", "v": 1, "id": "<hubId>", "name": "Linux PC", "port": 47616, "addrs": ["192.168.1.5"] }
```
Used for discovery sweeps and liveness checks. `GET /` returns a tiny HTML page that links to
`APP_URL` (plain text, no secrets).

### Encrypted ops

`POST /i6/<op>?d=<deviceId>` with `Content-Type: text/plain;charset=UTF-8` and the body being
`seal(key, requestAad(op, deviceId), json, binary).body`.

For pairing: `POST /i6/pair?h=<hubId>` and the key is `pairKey(token, hubId)`, AAD
`requestAad('pair', 'pair')`. The hub tries every currently valid token.

Successful response: `200 application/octet-stream`, body =
`seal(key, responseAad(op, requestIv), json, binary).body`, where `requestIv` is the `iv`
returned by `open()` on the request. Clients verify with the same AAD.

Error responses are plain JSON (not encrypted) `{ "error": "<code>" }` with status:
* `401 {"error":"unknown-device"}` / `{"error":"bad-auth"}` – the phone must show "Pairing lost –
  scan the QR again" and drop the hub record on `unknown-device`.
* `400 bad-request`, `404 not-found`, `413 too-large`, `500 internal`.

Clients encode the JSON/binary with `frame()` (`seal` does it). Binary is only used by `put`
(request) and `pull` (response).

| op | request JSON (+binary) | response JSON (+binary) |
|---|---|---|
| `pair` | `{deviceId, name, os}` | `{secret: b64url(S), hubId, name}` |
| `sync` | `{wait: 0..25000, name, os}` | `{name, addrs, outbox: [{tid, files:[{name,size,type,lastModified}]}]}` |
| `offer` | `{tid, files:[{name,size,type,lastModified}]}` | `{received: [bytesPerFile]}` |
| `put` | `{tid, i, offset}` + chunk bytes | `{bytes}` or `{error:'offset', bytes}` |
| `end` | `{tid}` | `{ok: true}` |
| `cancel` | `{tid}` | `{ok: true}` |
| `pull` | `{tid, i, offset, length}` | `{size}` + bytes |
| `pulled` | `{tid}` | `{ok: true}` |
| `unpair` | `{}` | `{ok: true}` |

Semantics:
* **sync** is a long poll and the heartbeat. The hub answers immediately if its outbox for the
  device is non-empty, otherwise holds the request up to `wait` ms (cap 25 s) and answers as
  soon as something is queued. It updates the device's `lastSeen`/name (shown as "online" in
  the hub UI while seen within 40 s).
* **offer** is idempotent per `tid` (random 24 hex chars from the phone). For an existing tid
  it returns how many bytes of each file the hub already has → the phone resumes from there.
  The hub picks the final file name at offer time (`cleanFileName`, de-duplicated with
  ` (1)`, ` (2)`… in the save folder).
* **put** appends `binary` to file `i` iff `offset` equals the hub's current byte count for that
  file; otherwise it changes nothing and answers `{error:'offset', bytes: <current>}` and the
  phone continues from `bytes`. Re-sending an already-written chunk is therefore harmless.
  Chunk size ≤ `CHUNK_SIZE` (4 MiB). When `bytes == size` the hub finalises that file
  (closes the writable, shows it in "Received", toasts).
* **end** marks the transfer complete (all files must be complete; otherwise `{ok:false}`).
* **cancel** discards partial data for the tid.
* **pull**: phone downloads hub→phone file `i` of outbox entry `tid` in chunks; `length` ≤
  `CHUNK_SIZE`. **pulled** removes the entry from the hub outbox.
* Hub keeps partial incoming transfers in memory (and their open writables) for at least
  1 hour of inactivity, so a phone that loses Wi-Fi or gets backgrounded resumes where it was.

## Reliability rules (both sides)

* Every network call has a timeout (`AbortSignal.timeout`): hello 1.5 s (sweep) / 4 s (direct),
  sync `wait + 10 s`, put/pull 60 s, others 15 s.
* Failures retry forever with `Backoff` (0.5 s → 30 s, jitter) while the transfer is pending
  and not cancelled; `online` / `visibilitychange→visible` events reset the backoff and retry
  immediately.
* **Locating the hub** (phone): try `lastAddr`, then all known `addrs`; after 2 consecutive
  failures, sweep the /24 of each known IPv4 address (`/i6/hello`, 1.5 s timeout, 32 in
  parallel) looking for a matching `id`; addresses learnt from `sync`/`hello` responses are saved.
* The phone persists queued outgoing transfers (including the `File` blobs) in the `queue`
  store, so they survive the app being killed and resume on next launch.
* Screen wake lock is held while a transfer is running.
